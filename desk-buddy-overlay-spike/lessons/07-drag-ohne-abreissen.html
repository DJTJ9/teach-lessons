DESK-BUDDY OVERLAY-SPIKE · LEKTION 07

Ziehen ohne Abreißen

Der Drag-Lock — warum die naive Umsetzung genau dann versagt, wenn der Nutzer schnell zieht

Der Bug, den fast jedes Desktop-Pet einmal hatte

Du drückst auf die Figur und ziehst schnell nach rechts. Das Fenster folgt — aber die Maus ist schneller als der Frame. Für einen Moment steht der Cursor neben der Figur, weil das Fenster noch nicht nachgezogen ist. Der Hit-Test aus Lektion 05 misst brav: „Cursor nicht über der Silhouette." Click-through geht an. Das Fenster bekommt keine Maus-Events mehr. Das Drag stirbt mitten in der Bewegung — die Figur reißt ab und bleibt liegen, während die Maus weiterzieht.

Frame n Cursor auf Figur → Click-through AUS → alles gut Frame n+1 Maus rast weiter, Fenster hinkt hinterher Cursor liegt neben der Figur → Hit-Test: "nicht drüber" → Click-through AN → keine Maus-Events mehr → Drag bricht ab Frame n+2 Figur steht still, Cursor ist weg. ABGERISSEN.

Das Fatale: Der Fehler tritt nur bei schneller Bewegung auf. Langsam ziehen funktioniert perfekt — die Sorte Bug, die man im Test nicht findet und die den Nutzer täglich trifft.

Die Lösung: ein Veto, das während des Ziehens gilt

Statt den Hit-Test zu beschleunigen (aussichtslos — das Fenster kann prinzipiell nicht schneller sein als der Cursor), friert der Spike die Entscheidung ein: Solange die Maustaste gedrückt ist, bleibt Click-through AUS, egal wo der Cursor steht. Das ist der DragLock.

Er ist ein einfaches bool-Property auf dem HitTestDriver — und der zweite Parameter im Zustandsautomaten aus Lektion 06: 

var desired = !(overOwn || dragLock);   // dragLock überstimmt die Ortsfrage

Ein Oder-Veto: „Cursor auf der Figur oder Drag läuft" → Klicks abfangen. Beim Loslassen fällt der Lock weg, der normale Hit-Test übernimmt sofort wieder.

Wer setzt den Lock? WindowDrag

[RequireComponent(typeof(Collider2D))]
public sealed class WindowDrag : MonoBehaviour
{
    public OverlayWindow Window { get; set; }
    public HitTestDriver Driver { get; set; }

    private bool _dragging;
    private Vector2Int _cursorStart;
    private Vector2Int _windowStart;

    private void OnMouseDown()
    {
        if (Window == null || !Window.IsActive) return;
        if (!Window.TryGetCursorScreen(out _cursorStart)) return;

        _windowStart = Window.Position;      // Startpunkte MERKEN, nicht Deltas addieren
        _dragging = true;
        if (Driver != null) Driver.DragLock = true;   // ← das Veto einschalten
    }

    private void Update()
    {
        if (!_dragging) return;

        if (!Input.GetMouseButton(0))            // losgelassen?
        {
            _dragging = false;
            if (Driver != null) Driver.DragLock = false;
            WindowState.Save(WindowState.DefaultDirectory, Window.Position);
            return;
        }

        if (!Window.TryGetCursorScreen(out var cursor)) return;
        Window.Position = new Vector2Int(
            _windowStart.x + (cursor.x - _cursorStart.x),
            _windowStart.y + (cursor.y - _cursorStart.y));
    }
}

Warum absolute Startpunkte statt Frame-Deltas?

Die naive Variante wäre, pro Frame die Mausbewegung seit dem letzten Frame auf die Fensterposition zu addieren. Das driftet: Jeder Rundungsfehler, jeder verpasste Frame, jeder Aufruf, der wegen TryGetCursorScreen == false aussteigt, geht dauerhaft verloren.

Der Spike merkt sich stattdessen beim Drücken zwei Ankerpunkte — wo der Cursor war (_cursorStart) und wo das Fenster war (_windowStart) — und rechnet in jedem Frame die Gesamtverschiebung neu aus. Ein ausgelassener Frame ist damit folgenlos: Der nächste stellt die korrekte Position wieder her. Absolut rechnen statt inkrementell — das gilt für jedes Drag, jeden Slider, jede Kamerabewegung.

Hier ist Unity-Input ausnahmsweise erlaubt OnMouseDown und Input.GetMouseButton(0) sind Unity-APIs — genau das, was Lektion 05 verboten hat. Der Unterschied ist die Voraussetzung: Ein Drag beginnt immer auf der Figur. Dort ist Click-through per Definition AUS, das Fenster bekommt also Maus-Events. Und sobald der Lock steht, bleibt es dabei — der Zustand, der die Unity-Events abwürgen würde, kann während des Drags gar nicht eintreten.

Die Position holt sich der Code trotzdem per TryGetCursorScreen: Sie muss in Bildschirmkoordinaten vorliegen, damit sie sich mit Window.Position verrechnen lässt. Und sie darf nicht an der Fenstergröße hängen — der Cursor verlässt das Fenster beim schnellen Ziehen ja regelmäßig.

Warum OnMouseDown, aber kein OnMouseUp?

Das Loslassen wird in Update per Input.GetMouseButton(0) abgefragt statt über OnMouseUp. Der Grund ist derselbe wie beim Abreißen: OnMouseUp feuert nur, wenn der Cursor beim Loslassen noch über dem Collider steht. Lässt der Nutzer 300 Pixel daneben los — was beim schnellen Ziehen ständig passiert — käme das Event nie. Der DragLock bliebe für immer an, und die Figur wäre dauerhaft klick-blockierend.

Merke: collider-gebundene Events sind für Drag-Enden ungeeignet OnMouseDown ist collider-gebunden und deshalb für den Start perfekt (dort ist der Cursor ja garantiert drüber). Für das Ende braucht man eine Quelle, die unabhängig von der Cursorposition ist. Dieselbe Logik gilt für OnMouseUpAsButton in ClickFeedback — das ist Absicht: Der Farbwechsel soll nur zählen, wenn man auf der Figur loslässt.

Das Zusammenspiel der drei Komponenten

Maustaste gedrückt (auf der Figur) │ ├─ WindowDrag.OnMouseDown() │ _cursorStart, _windowStart merken │ Driver.DragLock = true ──────────────┐ │ │ ▼ ▼ Jeder Frame: HitTestDriver.Update() WindowDrag.Update() overOwn = OverlapPoint(...) Window.Position = Start + Delta Evaluate(overOwn, dragLock: TRUE) → desired immer false → nach dem ersten Mal: null → KEIN nativer Call mehr Maustaste los ├─ DragLock = false ├─ WindowState.Save(...) ← Position sofort persistieren └─ nächster Frame: Hit-Test entscheidet wieder normal

Schön daran: Während des gesamten Drags passiert kein einziger nativer Style-Aufruf. Der Zustandsautomat liefert nach dem ersten false nur noch null. Die einzigen nativen Aufrufe im Drag sind GetCursorPos und SetWindowPos — genau die zwei, die man braucht.

Die verworfene Alternative: natives Fenster-Drag

Windows kann Fenster-Ziehen selbst. Man schickt dem Fenster beim Mausdruck die Nachricht WM_NCLBUTTONDOWN mit HTCAPTION — „behandle das, als hätte der Nutzer die Titelleiste gepackt". Windows übernimmt dann die komplette Zieh-Schleife: butterweich, kein Nachhinken, null eigener Code.

Der Spike hat das bewusst verworfen. Der Preis wäre gewesen: Während des Drags läuft eine Windows-eigene Modal-Schleife — deine Anwendung ist in dieser Zeit weitgehend außen vor. Keine Animation („Figur zappelt beim Hochheben"), kein Einrasten an Bildschirmkanten, keine Reaktion aufs Ziel. Für ein Desktop-Pet, dessen ganzer Sinn Reaktion ist, ist Kontrolle wichtiger als perfekte Weichheit.

Quiz

1. Was passiert ohne DragLock, wenn man schnell zieht?

Abreißen. Und es fängt sich nicht von selbst: Nach dem Umschalten kommen keine Maus-Events mehr an, das Drag ist tot. OnMouseDown hat den Drag zwar gestartet, aber Input.GetMouseButton(0) würde ohne Events auch nicht mehr aktualisiert.

2. Warum _windowStart + (cursor - _cursorStart) statt „Position += Frame-Delta"?

Kein Drift. Jeder Frame rechnet die Gesamtverschiebung seit dem Drücken neu aus. Ein übersprungener Frame (z. B. TryGetCursorScreen liefert false) hat null Langzeitwirkung. Window.Position hat sehr wohl einen Getter — er wird für _windowStart und fürs Speichern gebraucht.

3. Warum wird das Drag-Ende in Update geprüft und nicht in OnMouseUp?

„Weil OnMouseUp collider-gebunden ist: Es feuert nur, wenn der Cursor beim Loslassen noch über der Figur steht. Beim schnellen Ziehen ist er das oft nicht — dann käme das Event nie, der DragLock bliebe hängen und das Pet würde dauerhaft alle Klicks abfangen. Input.GetMouseButton(0) in Update ist positionsunabhängig."

Was du jetzt weißt

  • Der Abreiß-Bug: Beim schnellen Ziehen hinkt das Fenster nach, der Cursor verlässt die Silhouette, Click-through schaltet mitten im Drag um.
  • DragLock ist ein Veto in Evaluate(overOwn, dragLock) — während des Ziehens gilt die Ortsfrage nicht.
  • Absolut rechnen (Start-Anker + Gesamtdelta) statt Frame-Deltas addieren — driftfrei.
  • OnMouseDown ist für den Start richtig (Cursor garantiert drüber), fürs Ende braucht es Input.GetMouseButton in Update.
  • Während des Drags passiert kein nativer Style-Aufruf — der Automat liefert nur noch null.
  • Verworfen: natives Drag per WM_NCLBUTTONDOWN/HTCAPTION — weicher, aber ohne jede Kontrolle während der Bewegung.
