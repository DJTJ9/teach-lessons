DESK-BUDDY OVERLAY-SPIKE · LEKTION 05

Click-through und die Input-Falle

Warum Input.mousePosition hier strukturell nicht funktionieren kann — und wie der Hit-Test stattdessen gebaut ist

Das Ziel

Das Fenster ist 256×256 Pixel groß, die Figur füllt davon vielleicht die Hälfte. Für den Nutzer soll gelten:

  • Klick auf die Figur → Unity bekommt den Klick (Farbwechsel, Ziehen, Rechtsklick-Beenden).
  • Klick auf die durchsichtigen Ecken des Fensterrechtecks → der Klick landet im Fenster darunter, also im Browser oder Notepad.

Windows kennt dafür ein Bit: WS_EX_TRANSPARENT. Ist es gesetzt, ignoriert das Fenster Mauseingaben komplett — sie werden an das nächste Fenster darunter durchgereicht. Das Bit gilt aber für das ganze Fenster, nicht pro Pixel. Also muss man es umschalten, je nachdem, wo der Cursor gerade steht.

Der Trick, der die Sache halbiert Das Fenster ist klein und wandert mit der Figur mit (Lektion 07). Alles außerhalb des 256×256-Rechtecks ist damit ohnehin gratis „durchlässig" — dort ist schlicht kein Fenster. Der Toggle regelt nur noch die transparenten Ecken innerhalb des Rechtecks. Ein bildschirmfüllendes Overlay wäre teurer und hätte keinen Vorteil.

Die naheliegende Lösung — und warum sie strukturell bricht

Der offensichtliche Unity-Ansatz:

// SO NICHT — bricht nach genau einem Zustandswechsel
var world = _camera.ScreenToWorldPoint(Input.mousePosition);
var overOwn = Physics2D.OverlapPoint(world) != null;
window.SetClickThrough(!overOwn);

Das läuft im Editor tadellos. Im Build passiert Folgendes:

Frame 1 Cursor neben der Figur → overOwn = false → SetClickThrough(true) → WS_EX_TRANSPARENT gesetzt Frame 2 Fenster empfängt ab jetzt KEINE Maus-Nachrichten mehr. Unitys Input-System bekommt nichts → Input.mousePosition bleibt auf dem letzten bekannten Wert stehen. EINGEFROREN. Frame 3 overOwn = false (immer noch der alte Wert) … → Click-through bleibt an. FÜR IMMER.

Die Figur ist ab dem ersten Frame außerhalb ihrer selbst nicht mehr anklickbar. Und das Perfide: Es gibt keinen Fehler, kein Log, keinen Absturz — im Editor tritt der Effekt nicht einmal auf, weil dort die native Schicht abgeschaltet ist (Lektion 04). Man findet es erst im Build, per Hand.

Das Muster hinter der Falle Man baut eine Rückkopplung: Der Sensor (Unity-Input) wird von genau der Aktion abgeschaltet, die er auslöst. Ein Sensor, der von seinem eigenen Ergebnis abhängt, ist kein Sensor. Die Lösung ist immer dieselbe — eine Messquelle nehmen, die unabhängig vom geschalteten Zustand ist.

Die Lösung: global fragen statt lokal empfangen

GetCursorPos fragt nicht das Fenster, sondern das System: „Wo ist der Mauszeiger gerade auf dem Bildschirm?" Diese Antwort kommt unabhängig davon, ob irgendein Fenster Maus-Nachrichten bekommt. Sie friert nie ein. 

/// Cursor in Bildschirmkoordinaten (Ursprung oben-links).
public bool TryGetCursorScreen(out Vector2Int position)
{
    position = Vector2Int.zero;
    if (!Win32Interop.GetCursorPos(out var p)) return false;
    position = new Vector2Int(p.X, p.Y);
    return true;
}

Beachte das Try…-Muster: Der native Aufruf kann fehlschlagen (z. B. auf dem gesperrten Desktop), und dann liefert die Fassade ehrlich false statt einer erfundenen Position. Der Aufrufer steigt in dem Fall einfach aus diesem Frame aus — der Zustand bleibt, wie er war.

Die Koordinaten-Umrechnung — der fummelige Teil

Jetzt hat man eine Bildschirmposition, braucht aber eine Weltposition in der Unity-Szene. Dazwischen liegen zwei Unterschiede, die beide gleichzeitig zuschlagen:

Win32 (GetCursorPos)Unity (ScreenToWorldPoint)
Bezugspunktder ganze Bildschirmdas Fenster
Y-AchseUrsprung oben-links, wächst nach untenUrsprung unten-links, wächst nach oben

Beides zusammen ergibt genau zwei Zeilen — sie sind das Herz von HitTestDriver.Update():

var origin = Window.Position;     // Fensterecke oben-links, Bildschirmkoordinaten (GetWindowRect)
var size   = Window.ClientSize;   // Fenstergröße in Pixeln

// Win32: Ursprung oben-links. Unity: Ursprung unten-links, fensterrelativ.
var localX = cursor.x - origin.x;
var localY = size.y - (cursor.y - origin.y);

localX ist die reine Verschiebung. localY macht beides in einem Ausdruck: erst fensterrelativ (cursor.y - origin.y), dann umgedreht (size.y - …).

Bildschirm (Win32) Fenster (Unity) ┌───────────────────────────┐ │ (0,0) │ origin=(400,300) size=(256,256) │ ┌──────────┐ │ │ │ Fenster │ │ Cursor (500,350) auf dem Bildschirm │ │ ● │ │ localX = 500-400 = 100 │ └──────────┘ │ localY = 256-(350-300) = 206 │ Y ↓ │ Y ↑ └───────────────────────────┘
Warum GetWindowRect überhaupt in der Interop-Datei steht Diese Funktion fehlte in der ursprünglichen Design-Skizze und kam beim Planschreiben dazu — mit genau dieser Begründung: Ohne Fensterursprung und -höhe ist die Umrechnung unmöglich. Sie trägt gleich drei Dinge: Position (get), ClientSize und damit den ganzen Hit-Test.

Dass ClientSize hier einfach das Fensterrechteck nimmt, ist übrigens nur zulässig, weil das Fenster randlos ist (Lektion 03): Bei WS_POPUP gibt es keine Non-Client-Area, also sind Fenster-Rechteck und Client-Rechteck identisch. Mit Titelleiste bräuchte man GetClientRect + ClientToScreen.

Der Punkt-Test: OverlapPoint, nicht Raycast

var world = _camera.ScreenToWorldPoint(new Vector3(localX, localY, 0f));
var overOwn = Physics2D.OverlapPoint(world) != null;

Physics2D.OverlapPoint beantwortet direkt die gestellte Frage: „Liegt dieser Punkt in irgendeinem 2D-Collider?" Ein Raycast wäre das falsche Werkzeug — ein Strahl braucht eine Richtung, und in einer flachen 2D-Szene müsste man sich eine Z-Richtung ausdenken, die nichts bedeutet.

Der Collider ist im Spike ein CircleCollider2D auf dem Platzhalter-Sprite. Das ist die Definition der Figur-Silhouette: Was im Collider liegt, gilt als „auf der Figur". Für einen Kreis ist das exakt; für eine spätere Figur nimmt man mehrere Collider oder einen PolygonCollider2D.

Die verworfene Alternative: Alpha-Pixel-Hit-Test Man könnte statt eines Colliders den Alpha-Wert des gerenderten Pixels unter dem Cursor prüfen — pixelgenau, auch bei Löchern in der Figur. Der Spike hat das bewusst verworfen: teurer pro Frame, mehr Code, und für einen Kreis (und selbst für ein Pet mit Umriss) reicht ein Collider völlig. Der Collider hat außerdem einen Vorteil, den man erst später bemerkt: Man kann die klickbare Fläche absichtlich größer machen als die Figur — angenehmer zu treffen.

Der komplette Frame im Zusammenhang

private void Update()
{
    if (Window == null || !Window.IsActive) return;          // im Editor: hier ist Schluss
    if (!Window.TryGetCursorScreen(out var cursor)) return;      // nativer Fehlschlag → Frame überspringen

    var origin = Window.Position;
    var size   = Window.ClientSize;

    var localX = cursor.x - origin.x;
    var localY = size.y - (cursor.y - origin.y);

    var world   = _camera.ScreenToWorldPoint(new Vector3(localX, localY, 0f));
    var overOwn = Physics2D.OverlapPoint(world) != null;

    var change = _state.Evaluate(overOwn, DragLock);            // ← Lektion 06
    if (change.HasValue) Window.SetClickThrough(change.Value);
}

Auffällig: Die Methode allokiert nichts. Keine new-Objekte, keine Listen, keine Strings — nur Structs auf dem Stack. Bei 30 Frames pro Sekunde über Stunden hinweg ist das der Unterschied zwischen einem ruhigen Managed-Heap und einem Sägezahn, der irgendwann den GC weckt. Für ein Programm, das den ganzen Arbeitstag läuft, ist das keine Mikro-Optimierung, sondern Grundhygiene.

Die letzten zwei Zeilen sind der Grund, warum trotz Per-Frame-Messung fast nie ein nativer Aufruf passiert — das ist Lektion 06.

Quiz

1. Ein Kollege sagt: „Nimm doch einfach Input.mousePosition, das ist viel weniger Code." Deine Antwort in einem Satz?

„Sobald wir WS_EX_TRANSPARENT setzen, bekommt das Fenster keine Maus-Nachrichten mehr und Input.mousePosition friert auf dem letzten Wert ein — Click-through würde genau einmal einschalten und nie wieder aus; im Editor merkst du davon nichts, weil dort die native Schicht aus ist."

2. Warum size.y - (cursor.y - origin.y) und nicht cursor.y - origin.y?

Achsen-Spiegelung. cursor.y - origin.y macht die Position fensterrelativ, size.y - … dreht die Richtung um. Zwei Korrekturen in einem Ausdruck. (Physische vs. logische Pixel wären DPI-Scaling — bewusst außerhalb des Spike-Scopes.)

3. Wo im Code steht eigentlich die Definition „was gehört zur Figur"?

Im Collider. Physics2D.OverlapPoint kennt nur Collider — die Textur ist ihm egal. Deshalb kann man die klickbare Fläche auch bewusst größer oder kleiner als die sichtbare Figur machen.

Was du jetzt weißt

  • WS_EX_TRANSPARENT gilt fürs ganze Fenster → muss positionsabhängig umgeschaltet werden.
  • Die Input-Falle: Das Bit schaltet Unitys Maus-Input ab — Input.mousePosition friert ein, Click-through hängt für immer an.
  • Lösung: GetCursorPos fragt das System, nicht das Fenster — unabhängig vom geschalteten Zustand.
  • Zwei Korrekturen nötig: bildschirm→fensterrelativ und Y-Achse spiegeln.
  • GetWindowRect liefert Ursprung und Größe; bei WS_POPUP ist Fenster-Rect == Client-Rect.
  • Physics2D.OverlapPoint statt Raycast — Punkt-Frage, Punkt-Werkzeug. Der Collider ist die Silhouette.
  • Der Frame allokiert nichts — Pflicht für etwas, das stundenlang läuft.
