Das Transparenz-Rezept: DWM + Layered

OverlayWindow.Initialize() — sechs Schritte in einer Reihenfolge, die nicht beliebig ist

Die ganze Methode auf einen Blick

Das hier ist das Herzstück des Spikes. Alles, was ein Unity-Fenster in ein transparentes Overlay verwandelt, passiert in dieser einen Methode — 20 Zeilen: 

public void Initialize()
{
    if (Application.isEditor)
    {
        Debug.Log("[OverlayWindow] editor — skipping native setup");
        return;
    }

    _hwnd = Win32Interop.GetActiveWindow();
    if (_hwnd == IntPtr.Zero)
    {
        Debug.LogError("[OverlayWindow] GetActiveWindow returned NULL — no window handle");
        return;
    }

    SetBorderless();

    var margins = new Win32Interop.MARGINS { Left = -1, Right = -1, Top = -1, Bottom = -1 };
    Win32Interop.DwmExtendFrameIntoClientArea(_hwnd, ref margins);

    ApplyExStyle(false);
    Win32Interop.SetLayeredWindowAttributes(_hwnd, 0, 255, Win32Interop.LWA_ALPHA);

    SetTopMost(true);
}

Schritt für Schritt — und jeweils: warum genau hier?

Im Editor aussteigen

Der Unity-Editor kann Fenster-Transparenz nicht darstellen (Lektion 01), und GetActiveWindow() würde dort das Editor-Fenster liefern. Würde man darauf WS_POPUP setzen, verstümmelt man den Editor selbst — Titelleiste weg, Fenster randlos, im schlimmsten Fall unbenutzbar bis zum Neustart.

Der frühe return ist deshalb kein Komfort, sondern ein Schutzmechanismus. Er hat außerdem eine angenehme Folge: IsActive bleibt false, und jede andere Methode der Fassade steigt wegen if (!IsActive) return; ebenfalls aus. Der Play-Modus im Editor läuft also fehlerfrei durch, nur eben ohne Overlay-Verhalten.

Handle holen und ehrlich prüfen

GetActiveWindow() liefert das Fenster des aufrufenden Threads. Beim Start des Players ist das das Spielfenster. Kommt IntPtr.Zero zurück, gibt es kein Fenster — dann bricht die Methode ab und protokolliert das. Wichtig: Sie tut nicht so, als sei alles in Ordnung.

Alle folgenden Aufrufe hängen an diesem Handle. Ein SetWindowLongPtr auf IntPtr.Zero tut nichts und meldet nichts — man würde ewig suchen.

Rahmen entfernen (SetBorderless)

Muss vor dem DWM-Aufruf passieren. Grund: Der Rahmen bestimmt, wo Client-Area und Non-Client-Area liegen. Der nächste Schritt bezieht sich genau darauf — man ändert die Geometrie also zuerst und redet dann über sie, nicht umgekehrt. (Details zu WS_POPUP und SWP_FRAMECHANGED: Lektion 03.)

Den DWM-Rahmen über das ganze Fenster ziehen

var margins = new Win32Interop.MARGINS { Left = -1, Right = -1, Top = -1, Bottom = -1 };
Win32Interop.DwmExtendFrameIntoClientArea(_hwnd, ref margins);

Positive Werte bedeuten „zieh den Glas-Rahmen so viele Pixel weit in den Inhalt hinein". -1 auf allen vier Seiten ist der dokumentierte Sonderwert für „das ganze Fenster ist Rahmen" — englisch sheet of glass. Ab jetzt behandelt der DWM den Alpha-Kanal deines Fensterinhalts als echte Durchsichtigkeit.

Das ist die Stelle, an der die Player Settings aus Lektion 01 zuschlagen: Läuft die App unter D3D12 oder mit Flip-Model-Swapchain, geht dieser Aufruf ins Leere — ohne Fehler.

Extended Style setzen: Layered + Toolwindow, Click-through zunächst AUS

ApplyExStyle(false);   // WS_EX_LAYERED | WS_EX_TOOLWINDOW, ohne WS_EX_TRANSPARENT

WS_EX_LAYERED ist die Voraussetzung für den nächsten Schritt — ohne dieses Bit lehnt SetLayeredWindowAttributes ab. Der Parameter false ist eine bewusste Startbedingung: Das Fenster startet klickbar, nicht durchlässig. Die Hit-Test-Schleife (Lektion 05/06) schaltet ab dem ersten Frame selbst um.

Fenster-Deckkraft auf 255 setzen

Win32Interop.SetLayeredWindowAttributes(_hwnd, 0, 255, Win32Interop.LWA_ALPHA);

Das sieht auf den ersten Blick widersinnig aus — 255 heißt „voll deckend". Der Punkt ist die Unterscheidung zweier Alpha-Ebenen:

  • Fenster-Alpha (dieser Aufruf): eine globale Deckkraft für das gesamte Fenster. 255 = „nichts pauschal ausblenden".
  • Per-Pixel-Alpha (aus Schritt 4 + Kamera-Alpha 0): entscheidet Pixel für Pixel.

Man setzt hier also 255, um zu sagen: „Behandle das Fenster als Layered Window, aber verschleiere es nicht zusätzlich." Die eigentliche Durchsichtigkeit kommt vom DWM. Der zweite Parameter (key = 0) ist der Colorkey und wird ignoriert, weil das Flag LWA_ALPHA lautet und nicht LWA_COLORKEY.

Nebeneffekt, den man später brauchen kann: Genau diese Zahl ist der Hebel für ein Ein-/Ausblenden des ganzen Pets. Ein Wert von 128 macht die Figur halbtransparent — ohne einen einzigen Shader anzufassen.

Zum Schluss SetTopMost(true) (Lektion 03) — das Fenster ist jetzt randlos, transparent, klickbar und liegt oben.

  1. Zuerst prüfen, ob D3D11 wirklich aktiv ist (in ProjectSettings.asset darf Direct3D12 nicht vorkommen, useFlipModelSwapchain muss 0 sein). Das erklärt die meisten Fälle.
  2. Erst dann am Code drehen: SetLayeredWindowAttributes testweise ganz weglassen — also nur WS_EX_LAYERED + DwmExtendFrameIntoClientArea. Das ist die zweite gängige Variante.

Die Fassade: warum diese Methode nicht in einem MonoBehaviour steht

OverlayWindow ist eine schlichte C#-Klasse — kein MonoBehaviour, keine Szenen-Referenz. Sie ist die einzige Klasse im Projekt, die Win32Interop überhaupt kennt. Ihr öffentliches Gesicht ist absichtlich winzig:

Nichts davon riecht nach Windows. Es gibt kein IntPtr in der öffentlichen Signatur, kein hwnd, keine Bitmaske. Genau das ist der Zweck einer Fassade: Die Spiellogik spricht über Fenster, nicht über Win32. Was das für einen macOS-Port bedeutet, ist Thema von Lektion 08.

Zwei Kleinigkeiten in der Fassade, die man leicht überliest

SetClickThrough filtert doppelt: if (!IsActive || _clickThrough == enabled) return; — die Fassade merkt sich den letzten Zustand und ruft nativ nur bei echter Änderung. Die aufrufende Seite tut dasselbe noch einmal (Lektion 06). Doppelt gemoppelt? Nein: Die Fassade schützt sich selbst, unabhängig davon, wer sie benutzt.

ClientSize hat einen Fallback: Schlägt GetWindowRect fehl oder ist das Fenster inaktiv, liefert die Property new Vector2Int(Screen.width, Screen.height) statt Vector2Int.zero. Der Grund ist praktisch: Der Wert landet in einer Division bzw. einer Koordinatenumrechnung (Lektion 05) — eine 0 dort wäre viel schlimmer als eine plausible Näherung.

Quiz

1. Warum steht SetBorderless() vor DwmExtendFrameIntoClientArea?

Geometrie zuerst. Erst festlegen, was Rahmen und was Inhalt ist — dann dem DWM sagen, wie er mit dem Rahmen umgehen soll. Umgekehrt redet man über eine Geometrie, die man gleich danach ändert.

2. SetLayeredWindowAttributes(_hwnd, 0, 255, LWA_ALPHA) — warum 255 und nicht 0?

Erste Variante. Das ist die Fenster-Deckkraft, nicht die Pixel-Transparenz. 0 hieße: alles unsichtbar, auch die Figur. 255 heißt: „pauschal nichts ausblenden — entscheide pro Pixel." Ignoriert wird der Wert keineswegs; genau deshalb ist er ein guter Hebel für ein späteres Ein-/Ausblenden.

3. Warum ist der Application.isEditor-Ausstieg mehr als eine Bequemlichkeit?

„Weil GetActiveWindow() im Editor das Editor-Fenster liefert. Ohne den Ausstieg würde SetBorderless dem Unity-Editor selbst die Titelleiste wegnehmen und ihn topmost machen. Der return lässt IsActive auf false, wodurch alle anderen Methoden der Fassade ebenfalls sauber aussteigen — der Play-Modus läuft dann ohne Overlay-Verhalten, aber ohne Schaden."

Was du jetzt weißt

  • Die sechs Schritte von Initialize() in ihrer zwingenden Reihenfolge: Editor-Ausstieg → Handle → randlos → DWM-Extend → ExStyle → Layered-Alpha → topmost.
  • MARGINS(-1,-1,-1,-1) = „das ganze Fenster ist Rahmen" — der Sheet-of-Glass-Trick.
  • Fenster-Alpha (255) ≠ Per-Pixel-Alpha. Ersteres ist ein globaler Regler und ein guter Hebel für Fade-Effekte.
  • Start-Zustand ist klickbar (ApplyExStyle(false)), nicht durchlässig.
  • Der isEditor-Ausstieg schützt den Editor davor, selbst zum Overlay zu werden.
  • Die Fassade OverlayWindow hat kein IntPtr nach außen — das macht sie portierbar.
  • Bei schwarzem Hintergrund: erst Grafik-API prüfen, dann testweise SetLayeredWindowAttributes weglassen.
