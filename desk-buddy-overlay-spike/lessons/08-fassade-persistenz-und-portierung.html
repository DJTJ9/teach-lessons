Teil 1: Die Schichten und wer wen kennt

Die Pfeile zeigen nur nach unten. Win32Interop ist internal und wird ausschließlich von OverlayWindow benutzt; die Fassade wiederum hat keine einzige IntPtr in ihrer öffentlichen Signatur (Lektion 04). Deshalb kennt oberhalb der Fassade nichts mehr das Betriebssystem.

Teil 2: Persistenz — 40 Zeilen, die man überall wiederverwendet

Das Pet soll dort wieder auftauchen, wo man es hingestellt hat. Der Spike speichert dafür genau zwei Zahlen: 

/// JSON-Persistenz der Fensterposition. Verzeichnis wird injiziert, damit testbar.
public static class WindowState
{
    private const string FileName = "window.json";

    [Serializable]
    private struct Payload { public int x; public int y; }

    public static string DefaultDirectory => Application.persistentDataPath;

    public static void Save(string directory, Vector2Int position)
    {
        Directory.CreateDirectory(directory);
        var json = JsonUtility.ToJson(new Payload { x = position.x, y = position.y });
        File.WriteAllText(Path.Combine(directory, FileName), json);
    }

    public static bool TryLoad(string directory, out Vector2Int position)
    {
        position = Vector2Int.zero;
        var path = Path.Combine(directory, FileName);
        if (!File.Exists(path)) return false;

        try
        {
            var payload = JsonUtility.FromJson<Payload>(File.ReadAllText(path));
            position = new Vector2Int(payload.x, payload.y);
            return true;
        }
        catch (Exception e)
        {
            Debug.LogWarning($"[WindowState] unreadable {path}: {e.Message}");
            return false;
        }
    }
}

Drei Designentscheidungen, die kleiner aussehen, als sie sind:

EntscheidungWarum
Verzeichnis als Parameter, Default nur als Property Macht die Klasse testbar: Die Tests schreiben in ein temporäres Verzeichnis. Hätte man Application.persistentDataPath fest eingebaut, ginge kein EditMode-Test — und der Standardpfad wäre trotzdem nur eine Property entfernt.
TryLoad statt Load „Keine Datei da" ist beim ersten Start der Normalfall, kein Fehler. Der Aufrufer bekommt ein bool und entscheidet selbst — keine Exception für ein erwartetes Ereignis.
catch um das Parsen, mit LogWarning Eine korrupte Datei (abgestürzter Schreibvorgang, manuell editiert) darf den Start nicht verhindern. Das Pet landet dann an der Standardposition — und die Warnung steht im Log, statt still verschluckt zu werden.
Die vier Tests, die dazu gehören SaveThenLoadRoundTripsPosition · LoadWithoutFileReturnsFalse · LoadWithCorruptFileReturnsFalse (schreibt "{not json" in die Datei) · SaveOverwritesPreviousPosition.

Beachte, was nicht getestet wird: dass JsonUtility funktioniert. Getestet werden nur die eigenen Entscheidungen — Roundtrip, fehlende Datei, kaputte Datei, Überschreiben. Das ist derselbe Schnitt wie in Lektion 06: Teste, wo dein Denkfehler stecken kann, nicht die Bibliothek.

Wann wird gespeichert?

An zwei Stellen — bewusst redundant:

  • Beim Loslassen des Drags (WindowDrag.Update): sofort, damit ein Absturz die Position nicht kostet.
  • Beim Beenden (OverlayBootstrap.OnApplicationQuit): fängt Positionsänderungen ab, die nicht aus einem Drag stammen.

Teil 3: OverlayBootstrap — die Reihenfolge ist das Feature

public sealed class OverlayBootstrap : MonoBehaviour
{
    [SerializeField] private Camera overlayCamera;
    [SerializeField] private HitTestDriver hitTest;
    [SerializeField] private WindowDrag windowDrag;

    private const float TopMostReassertInterval = 5f;
    private readonly OverlayWindow _window = new OverlayWindow();

    private void Awake()
    {
        // 1. Laufverhalten: Messenger, nicht Spiel
        Application.targetFrameRate = 30;
        QualitySettings.vSyncCount  = 0;

        // 2. Kamera auf Alpha 0 (Lektion 01)
        if (overlayCamera == null) overlayCamera = Camera.main;
        overlayCamera.clearFlags      = CameraClearFlags.SolidColor;
        overlayCamera.backgroundColor = new Color(0f, 0f, 0f, 0f);
        overlayCamera.allowHDR  = false;
        overlayCamera.allowMSAA = false;

        // 3. Fenster nativ aufsetzen (Lektion 04)
        _window.Initialize();

        // 4. Erst JETZT die Abhängigen verdrahten — sie bekommen ein fertiges Fenster
        if (hitTest != null) hitTest.Window = _window;
        if (windowDrag != null)
        {
            windowDrag.Window = _window;
            windowDrag.Driver = hitTest;
        }

        // 5. Gespeicherte Position anwenden
        if (WindowState.TryLoad(WindowState.DefaultDirectory, out var saved))
            _window.Position = saved;

        // 6. Topmost dauerhaft halten (Lektion 03)
        InvokeRepeating(nameof(ReassertTopMost), TopMostReassertInterval, TopMostReassertInterval);
    }

    private void ReassertTopMost() => _window.SetTopMost(true);

    private void OnApplicationQuit()
    {
        if (_window.IsActive) WindowState.Save(WindowState.DefaultDirectory, _window.Position);
    }
}

Zwei Mechanismen sichern die Reihenfolge ab, die man sonst nur hofft:

Script Execution Order −100 Unity ruft Awake() aller Komponenten in undefinierter Reihenfolge auf. Würde HitTestDriver.Update() laufen, bevor _window.Initialize() durch ist, gäbe es Null-Referenzen oder — schlimmer — einen Frame mit falschem Zustand. Der Spike setzt die Ausführungsordnung deshalb hart auf −100 (also deutlich vor allen anderen), und zwar im Szenen-Generator: 
MonoImporter.SetExecutionOrder(MonoScript.FromMonoBehaviour(bootstrap), -100);

Der zweite Mechanismus ist die zentrale Verdrahtung: HitTestDriver und WindowDrag holen sich das Fenster nicht selbst (kein Singleton, kein FindObjectOfType), sondern bekommen es zugewiesen. Genau eine Klasse kennt die Reihenfolge, alle anderen sind passiv. Das ist der Grund, warum die beiden Komponenten in ihren Methoden mit if (Window == null || !Window.IsActive) return; beginnen — sie sind darauf ausgelegt, ohne Fenster einfach nichts zu tun (Editor-Fall).

Teil 4: Der Portierungsschnitt

Die Frage, für die die ganze Architektur gebaut ist: Was müsstest du anfassen, um dasselbe unter macOS laufen zu lassen?

DateiBeim Port
Win32Interop.csErsetzen — macOS-Äquivalent über Cocoa/Objective-C-Bridge
OverlayWindow.csInnenleben austauschen, öffentliche Signatur bleibt (oder Interface + zwei Implementierungen)
HitTestDriver.csunverändert
WindowDrag.csunverändert
WindowState.csunverändert (persistentDataPath ist plattformneutral)
OverlayBootstrap.csunverändert
Player Settingskomplett neu — die D3D11/Flip-Model-Frage ist rein Windows

Zwei von sieben Dateien. Das ist kein Zufall, sondern das Ergebnis von zwei Regeln, die von Anfang an galten: nur eine Datei mit DllImport und kein IntPtr in der öffentlichen Fassade.

Was der Spike bewusst NICHT gelöst hat Bevor du das in ein Produkt überführst, sind das die offenen Punkte — alle bewusst außerhalb des Spike-Scopes:
  • DPI-Scaling: Bei Skalierung ≠ 100 % können Win32-Pixel und Unity-Pixel auseinanderlaufen — die Koordinatenrechnung aus Lektion 05 braucht dann einen Faktor.
  • Multi-Monitor: Negative Bildschirmkoordinaten (Monitor links vom Hauptmonitor) funktionieren prinzipiell, aber eine gespeicherte Position auf einem abgezogenen Monitor macht das Pet unsichtbar. Es gibt keine Plausibilitätsprüfung beim Laden.
  • Autostart, Tray-Icon, Installer — nicht angefasst.
  • Der 30-Minuten-Dauertest steht mit dem gefixten Working-Set-Tracking noch aus; der erste Lauf hatte eine ~16-minütige Lücke (vermutlich Display-Standby) und die Working-Set-Spalte war wegen des Mono-Bugs komplett 0. managed_bytes zeigte ein normales Sägezahnmuster, die FPS lagen bei ~30 — Hinweis gegen ein Leck, kein Beweis.

Teil 5: Deine Checkliste für das nächste Overlay-Projekt

Wenn du diese Technik neu aufsetzt — in Unity oder woanders —, ist das die Reihenfolge, in der du am wenigsten Zeit verlierst:

  1. Umgebung zuerst, und verifizieren. D3D11 erzwingen, Flip-Model aus, Windowed, klein, nicht resizable. Danach in der Settings-Datei nachsehen, dass es wirklich drinsteht. Erst dann Code schreiben.
  2. Eine Plattform-Datei anlegen und die Regel „nur hier DllImport" von Anfang an durchhalten — auch wenn später ein Fix thematisch woanders hingehört.
  3. Fassade mit Fenster-Vokabular (Position, ClientSize, SetClickThrough) — kein IntPtr nach außen, im Editor no-op.
  4. Cursorposition global holen, nie über den Engine-Input, sobald Click-through im Spiel ist.
  5. Zustandsautomat für alles, was einen nativen Aufruf auslöst — bool?-Muster, Aufruf nur bei Kantenwechsel.
  6. DragLock von Anfang an. Der Abreiß-Bug kommt sonst garantiert, und zwar erst beim Nutzer.
  7. Beenden-Weg einbauen, bevor du WS_EX_TOOLWINDOW setzt.
  8. Diagnose mitlaufen lassen — und die Rohdaten einmal wirklich ansehen, statt nur „lief ohne Fehler" zu prüfen.
  9. Sichtbeweis von Hand: Notepad dahinter, danebenklicken, draufklicken, schnell ziehen, neu starten, Vollbild-Spiel dazwischen. Grüne Tests ersetzen das nicht.
Und ein Punkt, der nichts mit Code zu tun hat Beim Beweis-Durchlauf sollte automatisiert ein Vollbild-Screenshot als Nachweis entstehen. Auf dem echten Arbeitsrechner hat der prompt Browser-Tabs, eine private Chat-Konversation und ein Notepad-Fenster mit Klartext-Zugangsdaten mit erfasst; das Aufräumen danach hat zusätzlich ein ungespeichertes Dokument hart geschlossen. Abgebrochen, nichts committet, im README offen dokumentiert.

Beweisbilder auf einem Live-Desktop gehören dem Menschen. Entweder gezielt nur das Zielfenster aufnehmen — oder den Screenshot selbst machen.

Quiz

1. Warum nimmt WindowState.Save das Verzeichnis als Parameter, obwohl es immer Application.persistentDataPath ist?

Testbarkeit. Der Kommentar im Code sagt es wörtlich: „Verzeichnis wird injiziert, damit testbar." DefaultDirectory steht als Property daneben, der Produktivpfad ist also trotzdem nur ein Wort entfernt. Mehrere Pets wären ein netter Nebeneffekt, aber nicht die Absicht.

2. Was passiert ohne Script Execution Order −100 auf OverlayBootstrap?

Undefinierte Reihenfolge. Zwar laufen alle Awake vor allen Update, aber die Reihenfolge innerhalb der Awake-Phase ist nicht garantiert. Da OverlayBootstrap.Awake die anderen Komponenten verdrahtet, muss es zuverlässig zuerst laufen — sonst hängt es vom Zufall ab, ob im ersten Frame ein halb initialisierter Zustand sichtbar wird.

3. Du sollst dieselbe Technik für ein transparentes Notiz-Widget benutzen. Welche Dateien kopierst du unverändert, welche schreibst du neu?

„Win32Interop, OverlayWindow, HitTestDriver (inkl. ClickThroughState), WindowDrag und WindowState übernehme ich unverändert — das ist die komplette Overlay-Schicht. Neu schreibe ich nur die Szene, den Collider, der die klickbare Silhouette definiert, und den Bootstrap, weil dort projektspezifische Verdrahtung steht. Die Player Settings setze ich per Editor-Script identisch und verifiziere sie in der Settings-Datei, bevor ich überhaupt anfange."

Was du jetzt weißt

  • Vier Schichten, Abhängigkeiten nur nach unten: Spiellogik → Unity-Komponenten → Fassade → Plattform.
  • Persistenz: TryLoad statt Exception, Verzeichnis injiziert (testbar), catch mit Warnung statt Startabbruch. Gespeichert wird beim Loslassen und beim Beenden.
  • OverlayBootstrap besitzt die Reihenfolge: Framerate → Kamera-Alpha → Initialize() → Verdrahtung → gespeicherte Position → Topmost-Timer. Abgesichert per Execution Order −100.
  • Komponenten holen sich nichts selbst — zentrale Verdrahtung statt Singleton/Find, und jede beginnt mit einem IsActive-Ausstieg.
  • Portierung = 2 von 7 Dateien, weil DllImport und IntPtr nie nach oben durchgesickert sind.
  • Offen geblieben: DPI, Multi-Monitor, Autostart, sauberer 30-Minuten-Dauerlauf mit gefixtem Working-Set.
  • Neun-Punkte-Checkliste für dein nächstes Overlay — Umgebung zuerst und verifizieren, DragLock von Anfang an, Beenden-Weg vor WS_EX_TOOLWINDOW.
