DESK-BUDDY OVERLAY-SPIKE · LEKTION 06

Zustandsautomat statt Per-Frame-Call

14 Zeilen ClickThroughState — die einzige Stelle des Spikes, an der echte Logik wohnt (und die einzige, die man testen kann)

Das Problem: 30 native Aufrufe pro Sekunde für nichts

Der Hit-Test aus Lektion 05 läuft jeden Frame. Würde man sein Ergebnis direkt weitergeben, hieße das: 30 × SetWindowLongPtr pro Sekunde, dauerhaft, den ganzen Arbeitstag. Der Aufruf ist nicht teuer, aber er ist auch nicht gratis — und vor allem ist er unnötig: In 99 % der Frames hat sich gar nichts geändert. Der Cursor steht still oder bewegt sich innerhalb derselben Zone.

Interessant ist nur der Kantenwechsel: der Moment, in dem der Cursor die Silhouette betritt oder verlässt. Genau dafür gibt es einen kleinen Zustandsautomaten.

Der ganze Automat

/// Reine Entscheidungslogik des Click-through-Toggles — ohne Unity-Abhängigkeit,
/// damit der DragLock-Fall testbar ist.
/// Rückgabe null = kein Zustandswechsel, also kein nativer Call.
public sealed class ClickThroughState
{
    private bool _clickThrough;
    private bool _initialized;

    public bool? Evaluate(bool overOwn, bool dragLock)
    {
        var desired = !(overOwn || dragLock);
        if (_initialized && desired == _clickThrough) return null;
        _initialized = true;
        _clickThrough = desired;
        return desired;
    }
}

Das ist alles. Drei Entscheidungen stecken darin:

1. Der Rückgabetyp ist bool?, nicht bool

Drei mögliche Antworten statt zwei: true = „schalte Click-through ein", false = „schalte aus", null = „tu gar nichts". Der Nullable-Typ macht „keine Änderung" zu einem eigenständigen, nicht verwechselbaren Fall. Der Aufrufer wird dadurch zu einer Zeile: 

var change = _state.Evaluate(overOwn, DragLock);
if (change.HasValue) Window.SetClickThrough(change.Value);
Warum das mehr ist als ein Trick Die Alternative wäre gewesen, in HitTestDriver ein _lastOverOwn-Feld zu führen und dort zu vergleichen. Funktioniert auch — aber dann steckt die Entscheidungslogik in einem MonoBehaviour, das eine Kamera, ein Fenster und Physik-Zugriff braucht. Man kann sie nur noch im Build prüfen. So wie hier ist sie eine reine Klasse ohne eine einzige Unity-Abhängigkeit: zwei Bools rein, ein bool? raus.

2. _initialized erzwingt genau einen Aufruf am Anfang

Beim allerersten Evaluate ist _clickThrough per Default false. Ohne das Flag würde ein erster Aufruf mit desired == false als „keine Änderung" durchgehen — und der native Zustand wäre nie explizit gesetzt worden. Man würde sich auf einen Startwert verlassen, statt ihn zu schreiben. Das Flag stellt sicher: Der erste Frame setzt immer.

3. Die Wahrheitstabelle passt in eine Zeile

var desired = !(overOwn || dragLock);
overOwndragLockdesired (= Click-through)Bedeutung
falsefalsetrueCursor daneben, kein Drag → Klicks durchlassen
truefalsefalseCursor auf der Figur → Klicks abfangen
falsetruefalseDrag läuft, Cursor abgerutscht → trotzdem abfangen
truetruefalseDrag läuft auf der Figur → abfangen

Zeile 3 ist der eigentliche Grund für diese Klasse. Warum sie so aussehen muss, ist Lektion 07 — hier zählt: Der DragLock ist ein Veto, das die Ortsfrage überstimmt.

Warum das die einzige testbare Stelle im Spike ist

Der Spike besteht aus sieben Runtime-Dateien. Sechs davon hängen entweder am Betriebssystem (Win32Interop, OverlayWindow), an einem laufenden Fenster (HitTestDriver, WindowDrag, OverlayBootstrap) oder schreiben Dateien (IdleProbe). Sie lassen sich nicht sinnvoll automatisiert prüfen — Transparenz ist im Editor prinzipiell nicht darstellbar, und einen DllImport-Wrapper zu mocken hieße, Attrappen gegen sich selbst zu testen.

Bleiben zwei Stellen mit echter Logik: ClickThroughState und die JSON-Persistenz WindowState (Lektion 08). Genau diese zwei haben Tests — 7 + 4 Stück, alle grün. Der Spike hat den Testschnitt also nicht nach Abdeckungsquote gewählt, sondern nach der Frage: Wo kann überhaupt ein Denkfehler stecken?

Die sieben Tests als Spezifikation gelesen

Diese Tests sind vor der Implementierung geschrieben worden. Man kann sie deshalb wie eine Anforderungsliste lesen — jeder Test ist ein Satz über gewünschtes Verhalten: 

[Test] public void FirstEvaluationAlwaysReportsChange()
{
    var state = new ClickThroughState();
    Assert.AreEqual(true, state.Evaluate(overOwn: false, dragLock: false));
}

[Test] public void RepeatedSameInputReportsNoChange()
{
    var state = new ClickThroughState();
    state.Evaluate(false, false);
    Assert.IsNull(state.Evaluate(false, false));   // ← "kein nativer Call" als Testaussage
    Assert.IsNull(state.Evaluate(false, false));
}

[Test] public void EnteringOwnSpriteDisablesClickThrough()
{
    var state = new ClickThroughState();
    state.Evaluate(false, false);
    Assert.AreEqual(false, state.Evaluate(overOwn: true, dragLock: false));
}

[Test] public void LeavingOwnSpriteReEnablesClickThrough()  // ← genau der Bug aus Lektion 05
{
    var state = new ClickThroughState();
    state.Evaluate(false, false);
    state.Evaluate(true, false);
    Assert.AreEqual(true, state.Evaluate(overOwn: false, dragLock: false));
}

[Test] public void DragLockKeepsClickThroughOffEvenOutsideSprite()
{
    var state = new ClickThroughState();
    state.Evaluate(false, false);
    state.Evaluate(true, false);
    Assert.IsNull(state.Evaluate(overOwn: false, dragLock: true));   // Cursor raus, aber Drag hält → nichts tun
    Assert.IsNull(state.Evaluate(overOwn: false, dragLock: true));
}

[Test] public void ReleasingDragOutsideSpriteReEnablesClickThrough()
{
    var state = new ClickThroughState();
    state.Evaluate(false, false);
    state.Evaluate(true, false);
    state.Evaluate(false, true);
    Assert.AreEqual(true, state.Evaluate(overOwn: false, dragLock: false));  // Loslassen außerhalb → wieder durchlässig
}

[Test] public void DragLockFromOutsideAlsoDisablesClickThrough()
{
    var state = new ClickThroughState();
    state.Evaluate(false, false);
    Assert.AreEqual(false, state.Evaluate(overOwn: false, dragLock: true));
}
Was diese Tests wirklich absichern Nicht „der Code tut, was er tut" — sondern die vier Szenarien, die man im Handtest nur schwer reproduziert: schnelles Ziehen über den Silhouettenrand hinaus, Loslassen außerhalb, Drag-Start neben der Figur, und der allererste Frame. Genau das sind die Momente, in denen ein Desktop-Pet „abreißt" oder klick-tot wird. Ein Test, den man von Hand nur mit Glück auslöst, ist wertvoller als zehn, die den Normalfall abdecken.

Zwei Typen in einer Datei — Absicht, kein Zufall

HitTestDriver.cs enthält beide Klassen: die reine ClickThroughState und das MonoBehaviour HitTestDriver. Die Aufteilung folgt einer klaren Linie:

HitTestDriver (MonoBehaviour) ClickThroughState (reine Klasse) ───────────────────────────── ──────────────────────────────── Kamera, Physik, Fenster zwei bool rein, bool? raus fragt jeden Frame ab merkt sich den letzten Zustand "WO ist der Cursor?" "MUSS sich etwas ändern?" nur im Build prüfbar 7 EditMode-Tests, ohne Unity

Für die Test-Assembly ist übrigens eine Kleinigkeit Voraussetzung, die man beim Nachbauen leicht übersieht: Eine Test-asmdef kann nicht auf die Standard-Assembly Assembly-CSharp referenzieren. Deshalb hat der Spike eine eigene Assets/Scripts/DeskBuddy.asmdef für den Runtime-Code — sonst gäbe es schlicht nichts, worauf die Tests zeigen könnten. 

// Assets/Tests/EditMode/DeskBuddy.Tests.EditMode.asmdef
{
    "name": "DeskBuddy.Tests.EditMode",
    "references": ["DeskBuddy", "UnityEngine.TestRunner", "UnityEditor.TestRunner"],
    "includePlatforms": ["Editor"],
    "overrideReferences": true,
    "precompiledReferences": ["nunit.framework.dll"],
    "autoReferenced": false,
    "defineConstraints": ["UNITY_INCLUDE_TESTS"]
}
Grüne Tests sind hier kein Beweis Alle 11 Tests grün heißt: Die Entscheidungslogik und die Persistenz stimmen. Es heißt nicht, dass das Overlay funktioniert. Ob der Hintergrund wirklich durchsichtig ist, ob Klicks wirklich durchgehen, ob die Figur beim Ziehen hält — das sieht nur ein Mensch vor einem Build. Der Spike hat deshalb einen Neun-Punkte-Durchlauf von Hand als alleiniges Fertig-Kriterium definiert, ausdrücklich nicht die Testsuite.

Quiz

1. Warum gibt Evaluate bool? zurück statt bool?

Erste Variante. null heißt „nichts zu tun" — daraus wird beim Aufrufer if (change.HasValue). So passieren native Aufrufe nur bei echten Kantenwechseln statt 30-mal pro Sekunde.

2. Du löschst das Feld _initialized. Was passiert?

Erste Variante. Ohne das Flag gilt der Default _clickThrough == false als „bereits gesetzt". Startet die App mit dem Cursor neben der Figur, wäre desired == true — das würde gemeldet. Startet sie mit dem Cursor auf der Figur, wäre desired == false und die Antwort null: kein Aufruf, obwohl der native Zustand nie geschrieben wurde. Genau das prüft FirstEvaluationAlwaysReportsChange.

3. Warum ist ClickThroughState eine eigene Klasse und keine drei Felder im HitTestDriver?

„Weil sie damit keine Unity-Abhängigkeit hat — kein MonoBehaviour, keine Kamera, keine Physik. Sie ist zwei Bools rein, ein bool? raus und deshalb in EditMode-Tests prüfbar. Im HitTestDriver steckt alles, was nur im Build lebt; in ClickThroughState steckt alles, wo ein Denkfehler möglich ist. Genau an dieser Grenze verläuft die Testbarkeit."

Was du jetzt weißt

  • Kantenwechsel statt Zustand: nativer Aufruf nur, wenn sich wirklich etwas ändert — sonst 30 Calls/Sekunde für nichts.
  • bool? macht „keine Änderung" zu einem eigenen Fall; der Aufrufer schrumpft auf zwei Zeilen.
  • _initialized erzwingt, dass der erste Frame den nativen Zustand schreibt, statt ihn anzunehmen.
  • desired = !(overOwn || dragLock) — DragLock ist ein Veto über die Ortsfrage.
  • Der Testschnitt folgt der Frage „wo kann ein Denkfehler stecken", nicht einer Abdeckungsquote: 7 Tests hier, 4 für die Persistenz, sonst keine.
  • Eine Test-asmdef braucht eine eigene Runtime-asmdef — Assembly-CSharp ist nicht referenzierbar.
  • Grüne Tests ≠ funktionierendes Overlay. Der Sichtbeweis bleibt Handarbeit.
