DESK-BUDDY OVERLAY-SPIKE · LEKTION 02

Win32 von Null: HWND, DllImport, Bitmasken

Win32Interop.cs Zeile für Zeile — die einzige Datei im Projekt, die das Betriebssystem direkt anfasst

Die Ausgangslage

Unity kann alles, was im Fenster passiert. Was das Fenster selbst ist — Rahmen, Position, Z-Reihenfolge, ob Klicks ankommen — weiß nur Windows. Für diese Fragen gibt es keine Unity-API. Man muss mit dem Betriebssystem reden, und zwar über die Win32-API: eine Sammlung von C-Funktionen in System-DLLs, die es seit den 90ern gibt und die sich seither nicht geändert hat.

Diese Lektion baut die dafür nötigen vier Konzepte von Null auf — Handle, P/Invoke, Struct-Layout, Bitmaske — und liest damit die komplette Interop-Datei des Spikes.

Konzept 1: Das Handle (HWND)

Windows gibt dir keine Objekte, sondern Handles: undurchsichtige Zahlen, die intern auf eine Systemressource zeigen. Ein HWND ist ein Fenster-Handle. Du kannst damit nichts anfangen außer: es an andere Win32-Funktionen weiterzureichen. Auf C#-Seite ist das ein IntPtr — ein Zeiger-großer Integer (auf x64: 64 Bit). 

private IntPtr _hwnd = IntPtr.Zero;   // Zero == "kein Fenster", die übliche Null-Prüfung
public bool IsActive => _hwnd != IntPtr.Zero;

Woher bekommt man das eigene Handle? Der Spike nimmt GetActiveWindow() — sie liefert das Fenster, das dem aufrufenden Thread gerade gehört. Beim Start eines Unity-Players ist das genau das Spielfenster.

Warum nicht FindWindow("UnityWndClass", productName)? Das ist die andere gängige Variante — sie sucht ein Fenster nach Klassenname und Titel. Sie funktioniert auch, hat aber zwei Schwächen: Sie kann bei mehreren Instanzen oder gleichnamigen Fenstern das falsche treffen, und sie hängt am Produktnamen. GetActiveWindow braucht keine Namen — der Preis ist, dass sie nur stimmt, solange man sie früh aufruft, während das eigene Fenster aktiv ist. Genau deshalb läuft die Initialisierung im Spike in Awake() mit Script Execution Order −100 (Lektion 08).

Konzept 2: P/Invoke — C#-Funktionen, die in einer DLL leben

P/Invoke (Platform Invoke) ist der .NET-Mechanismus, um eine native C-Funktion aufzurufen. Du deklarierst eine Methode ohne Rumpf, markierst sie extern und sagst per Attribut, in welcher DLL sie steckt. Die Laufzeit sucht das Symbol beim ersten Aufruf und übersetzt die Argumente (das nennt man Marshalling). 

[DllImport("user32.dll")]
internal static extern IntPtr GetActiveWindow();

Drei Details, die man beim Lesen sofort erkennen sollte:

SchreibweiseBedeutung
[DllImport("user32.dll")] Fensterverwaltung. dwmapi.dll = Composition, kernel32.dll = Prozesse/System, psapi.dll = Prozess-Statistiken.
EntryPoint = "SetWindowLongPtrW" Der echte Symbolname in der DLL weicht vom C#-Namen ab. Das W steht für die Unicode-Variante (es gibt fast immer ein …A für ANSI und ein …W für Wide/UTF-16 — nimm immer W).
[return: MarshalAs(UnmanagedType.Bool)] Win32 gibt BOOL zurück — das ist ein 4-Byte-Int, nicht das 1-Byte-bool von C#. Ohne diese Angabe liest .NET unter Umständen das falsche Byte. Sicherheitsgurt, kostet nichts.

Konzept 3: Structs mit festem Speicherlayout

Manche Funktionen schreiben ihr Ergebnis nicht in den Rückgabewert, sondern in eine Struktur, deren Adresse du übergibst. Damit das klappt, muss das C#-Struct byteweise dem C-Struct entsprechen. Der C#-Compiler darf Felder normalerweise umsortieren — [StructLayout(LayoutKind.Sequential)] verbietet ihm das. 

[StructLayout(LayoutKind.Sequential)]
internal struct POINT { public int X; public int Y; }

[StructLayout(LayoutKind.Sequential)]
internal struct RECT { public int Left; public int Top; public int Right; public int Bottom; }

[StructLayout(LayoutKind.Sequential)]
internal struct MARGINS { public int Left; public int Right; public int Top; public int Bottom; }
Die Reihenfolge ist Teil des Vertrags MARGINS ist Left, Right, Top, Bottom — nicht die gewohnte Uhrzeigersinn-Reihenfolge, und auch nicht dieselbe wie bei RECT (Left, Top, Right, Bottom). Wer hier zwei Felder vertauscht, bekommt keinen Compilerfehler und keine Exception, sondern falsche Zahlen. Immer gegen die Microsoft-Doku abgleichen, nie aus dem Gedächtnis tippen.

Beim Aufruf markiert man solche Parameter mit out (Funktion füllt sie) oder ref (Funktion liest und schreibt): 

[DllImport("user32.dll")]
[return: MarshalAs(UnmanagedType.Bool)]
internal static extern bool GetCursorPos(out POINT point);

[DllImport("user32.dll")]
[return: MarshalAs(UnmanagedType.Bool)]
internal static extern bool GetWindowRect(IntPtr hWnd, out RECT rect);

[DllImport("dwmapi.dll")]
internal static extern int DwmExtendFrameIntoClientArea(IntPtr hWnd, ref MARGINS margins);

Konzept 4: Bitmasken — wie Windows Eigenschaften speichert

Ein Fenster hat dutzende Ja/Nein-Eigenschaften: sichtbar, Rahmen, Titelleiste, Minimierbar, Layered, Klick- durchlässig … Windows packt sie nicht in Felder, sondern in zwei Zahlen: den Style und den Extended Style. Jedes Bit dieser Zahlen ist eine Eigenschaft. 

// Style (GWL_STYLE)
internal const long WS_POPUP   = 0x80000000L;  // Fenster ohne Rahmen/Titelleiste
internal const long WS_VISIBLE = 0x10000000L;  // sichtbar

// Extended Style (GWL_EXSTYLE)
internal const long WS_EX_LAYERED     = 0x00080000L; // über Zwischenschicht komponiert → Alpha erlaubt
internal const long WS_EX_TRANSPARENT = 0x00000020L; // Mausklicks gehen durch (Lektion 05)
internal const long WS_EX_TOOLWINDOW  = 0x00000080L; // kein Taskleisten-Eintrag, nicht im Alt+Tab

Kombiniert wird mit | (bitweises Oder = „beide Eigenschaften an"), geprüft mit &. Im Spike sieht das so aus — eine Zeile, die den Unterschied zwischen „klickbar" und „durchlässig" macht: 

long ex = WS_EX_LAYERED | WS_EX_TOOLWINDOW;
if (clickThrough) ex |= WS_EX_TRANSPARENT;

0x00080000 | 0x00000080 = 0x00080080  →  mit Transparent: 0x000800A0

Warum long und nicht int? WS_POPUP ist 0x80000000 — das oberste Bit eines 32-Bit-Werts. Als int wäre das negativ, und beim Verrechnen mit anderen Konstanten holt man sich Vorzeichen-Ärger. Deshalb long für die Konstanten und erst am Ende die Umwandlung nach IntPtr.

Die Setter: SetWindowLongPtr und SetWindowPos

internal const int GWL_STYLE   = -16;  // "welche der Zahlen?" → Style
internal const int GWL_EXSTYLE = -20;  // → Extended Style

[DllImport("user32.dll", EntryPoint = "SetWindowLongPtrW")]
internal static extern IntPtr SetWindowLongPtr(IntPtr hWnd, int index, IntPtr value);

[DllImport("user32.dll", EntryPoint = "GetWindowLongPtrW")]
internal static extern IntPtr GetWindowLongPtr(IntPtr hWnd, int index);

Die negativen Indizes sind kein Tippfehler — Win32 adressiert die Fenster-Eigenschaften über negative Offsets. Merken muss man nur diese zwei. Hinweis: Die …Ptr-Varianten existieren als echte Exporte nur in 64-Bit-Windows; deshalb baut der Spike ausschließlich StandaloneWindows64 und spart sich einen 32-Bit-Fallback.

SetWindowPos ist der Allzweck-Fensterbefehl: Position, Größe und Z-Reihenfolge in einem Aufruf. Weil man selten alles gleichzeitig will, gibt es Flags, die einzelne Parameter für ungültig erklären: 

internal const uint SWP_NOSIZE      = 0x0001; // cx/cy ignorieren
internal const uint SWP_NOMOVE      = 0x0002; // x/y ignorieren
internal const uint SWP_NOACTIVATE  = 0x0010; // Fenster NICHT in den Fokus holen ← wichtig fürs Pet
internal const uint SWP_FRAMECHANGED= 0x0020; // "Stil hat sich geändert, Rahmen neu berechnen"
internal const uint SWP_SHOWWINDOW  = 0x0040;

internal static readonly IntPtr HWND_TOPMOST = new IntPtr(-1); // Pseudo-Handle: "ganz nach oben"

[DllImport("user32.dll")]
[return: MarshalAs(UnmanagedType.Bool)]
internal static extern bool SetWindowPos(IntPtr hWnd, IntPtr hWndInsertAfter,
    int x, int y, int cx, int cy, uint flags);
Das Muster, das du überall wiedersehen wirst „Verschiebe das Fenster, ändere aber nicht die Größe und stiehl nicht den Fokus" heißt: SetWindowPos(hwnd, IntPtr.Zero, x, y, 0, 0, SWP_NOSIZE | SWP_NOACTIVATE). Die beiden Nullen für Breite/Höhe sind Attrappen — SWP_NOSIZE macht sie bedeutungslos.

Die restlichen zwei: SetLayeredWindowAttributes und DwmExtendFrameIntoClientArea

internal const uint LWA_ALPHA = 0x00000002;  // "der alpha-Parameter gilt" (statt Colorkey)

[DllImport("user32.dll")]
[return: MarshalAs(UnmanagedType.Bool)]
internal static extern bool SetLayeredWindowAttributes(IntPtr hWnd, uint key, byte alpha, uint flags);

Diese beiden sind die eigentlichen Transparenz-Aufrufe — ihre Reihenfolge und ihr Zusammenspiel sind Lektion 04. Hier reicht: Sie stehen in derselben Datei wie alles andere Native.

Der Nachzügler: psapi und ein stiller Mono-Bug

Der Spike loggt alle 10 Sekunden Speicherverbrauch mit, um nach 30 Minuten Leerlauf ein Speicherleck ausschließen zu können. Der naheliegende C#-Weg dafür ist Process.GetCurrentProcess().WorkingSet64. Im gebauten Player mit dem Mono-Backend liefert der aber durchgängig 0 — keine Exception, kein Log, nur eine plausibel aussehende falsche Zahl. Aufgefallen ist das erst beim Blick in die CSV-Rohdaten.

Der Fix holt den Wert direkt beim Betriebssystem — und zwar bewusst in dieser Datei, um die Regel „nur eine Datei enthält DllImport" nicht aufzuweichen: 

[StructLayout(LayoutKind.Sequential)]
internal struct PROCESS_MEMORY_COUNTERS
{
    public uint cb;                          // Größe der Struktur — Versions-Handshake
    public uint PageFaultCount;
    public UIntPtr PeakWorkingSetSize;
    public UIntPtr WorkingSetSize;             // ← der gesuchte Wert
    public UIntPtr QuotaPeakPagedPoolUsage;
    public UIntPtr QuotaPagedPoolUsage;
    public UIntPtr QuotaPeakNonPagedPoolUsage;
    public UIntPtr QuotaNonPagedPoolUsage;
    public UIntPtr PagefileUsage;
    public UIntPtr PeakPagefileUsage;
}

[DllImport("kernel32.dll")]
internal static extern IntPtr GetCurrentProcess();

[DllImport("psapi.dll", SetLastError = true)]
private static extern bool GetProcessMemoryInfo(IntPtr hProcess, out PROCESS_MEMORY_COUNTERS counters, uint size);

/// Bypasses System.Diagnostics.Process — under Mono on Windows, Process.WorkingSet64 silently returns 0.
internal static ulong GetWorkingSetBytes()
{
    var counters = new PROCESS_MEMORY_COUNTERS();
    counters.cb = (uint)Marshal.SizeOf(typeof(PROCESS_MEMORY_COUNTERS));
    if (!GetProcessMemoryInfo(GetCurrentProcess(), out counters, counters.cb)) return 0;
    return (ulong)counters.WorkingSetSize;
}

Drei Dinge, die man hier lernt und überall wiederverwenden kann: (1) Das cb-Feld ist ein Versions-Handshake — viele Win32-Structs beginnen damit, und man füllt es immer per Marshal.SizeOf, nie mit einer getippten Zahl. (2) UIntPtr statt ulong, weil SIZE_T zeigergroß ist — auf x86 4, auf x64 8 Byte. (3) SetLastError = true sorgt dafür, dass man den Windows-Fehlercode nachträglich per Marshal.GetLastWin32Error() abfragen könnte.

Die eigentliche Lehre ist nicht der Fix Ein Messwert, der immer 0 ist, sieht in einer CSV genauso „ordentlich" aus wie ein echter Messwert. Der Spike hätte Punkt „kein Speicherwachstum" grün abhaken können, ohne je etwas gemessen zu haben. Wenn eine Diagnose keinen Fehler wirft, ist sie damit noch nicht richtig. Rohdaten einmal selbst anschauen — nicht nur „lief durch" prüfen.

Die Architektur-Regel dahinter

Alles oben steht in genau einer Datei: Assets/Scripts/Platform/Win32Interop.cs, internal static class. Kein anderer Ort im Projekt darf DllImport enthalten. Der Grund ist nicht Ordnungsliebe:

  • Portierbarkeit: Ein macOS- oder Linux-Port ersetzt genau diese eine Datei. Alles darüber bleibt unverändert.
  • Testbarkeit: Was P/Invoke berührt, ist nur im Build prüfbar. Je kleiner diese Fläche, desto mehr Logik lässt sich normal testen (Lektion 06).
  • Fehlersuche: Kommt eine falsche Zahl aus dem System, gibt es genau einen Ort zum Nachschauen.

Der Spike hat diese Regel unter Druck gehalten: Als der Working-Set-Fix nötig wurde, wanderte er in die Interop-Datei — nicht in die Diagnose-Klasse, wo er thematisch hingehört hätte.

Quiz

1. Warum steht [return: MarshalAs(UnmanagedType.Bool)] über den bool-Funktionen?

Größenunterschied. Win32-BOOL ist ein 32-Bit-Int. Das Attribut sagt dem Marshaller explizit, wie er das umrechnen soll. Pflicht ist es nicht (der Default für bool ist in der Praxis derselbe) — aber es macht die Absicht sichtbar und schützt vor Überraschungen.

2. Du willst ein Fenster nach vorn holen, ohne es zu verschieben, ohne die Größe zu ändern und ohne ihm den Tastaturfokus zu geben. Welche Flags?

Erste Variante — exakt die Zeile aus OverlayWindow.SetTopMost. Ohne NOMOVE/NOSIZE würden die übergebenen Nullen als „Position 0,0 und Größe 0×0" gelten. Ohne NOACTIVATE springt der Fokus weg — bei einem alle 5 Sekunden feuernden Timer (Lektion 03) wäre das unbenutzbar.

3. Ein Kollege will GetWorkingSetBytes() nach IdleProbe.cs verschieben, „weil es dort thematisch hingehört". Was antwortest du?

„Thematisch stimmt das, aber dann enthält eine zweite Datei DllImport — und die Regel ‚genau eine Plattform-Datei' ist genau das, was einen späteren macOS-Port zu einem Ein-Datei-Austausch macht. Der Aufruf Win32Interop.GetWorkingSetBytes() steht ja in IdleProbe; nur das DllImport bleibt gekapselt."

Was du jetzt weißt

  • HWND = undurchsichtiges Fenster-Handle, in C# ein IntPtr; IntPtr.Zero ist die Null-Prüfung.
  • P/Invoke: [DllImport] + extern, EntryPoint für …W-Namen, MarshalAs für Typgrößen.
  • StructLayout(Sequential) erzwingt die Feldreihenfolge — Reihenfolge ist Teil des Vertrags (MARGINS ≠ RECT).
  • Bitmasken: Style und Extended Style sind je eine Zahl; kombiniert mit |. GWL_STYLE = -16, GWL_EXSTYLE = -20.
  • SetWindowPos ist Position + Größe + Z-Order in einem — SWP_NO…-Flags schalten aus, was du nicht meinst.
  • Mono-Falle: Process.WorkingSet64 liefert im Windows-Build still 0; echter Wert über psapi!GetProcessMemoryInfo.
  • Eine Datei, alle DllImports — die Regel, die einen Port zu einem Datei-Austausch macht.
