DESK-BUDDY OVERLAY-SPIKE · LEKTION 03

Randlos und immer oben

WS_POPUP, SWP_FRAMECHANGED, HWND_TOPMOST — und warum „immer oben" eine Lüge ist, die man alle 5 Sekunden nachschieben muss

Teil 1: Den Rahmen loswerden

Ein normales Fenster besteht aus zwei Bereichen: der Client-Area (dein Inhalt) und der Non-Client-Area (Titelleiste, Rahmen, Minimieren/Maximieren/Schließen). Die Non-Client-Area zeichnet Windows, nicht du. Für ein Desktop-Pet muss sie weg — sonst schwebt der Kreis in einem sichtbaren Kasten.

Der Schalter dafür ist der Fenster-Style. Statt einzelne Bits abzuziehen, setzt der Spike den Style komplett neu — er weiß ja, was er will: 

public void SetBorderless()
{
    if (!IsActive) return;
    var style = new IntPtr(Win32Interop.WS_POPUP | Win32Interop.WS_VISIBLE);
    Win32Interop.SetWindowLongPtr(_hwnd, Win32Interop.GWL_STYLE, style);
    Win32Interop.SetWindowPos(_hwnd, IntPtr.Zero, 0, 0, 0, 0,
        Win32Interop.SWP_NOMOVE | Win32Interop.SWP_NOSIZE |
        Win32Interop.SWP_NOACTIVATE | Win32Interop.SWP_FRAMECHANGED);
}

Zwei Zeilen, zwei Lehren:

WS_POPUP | WS_VISIBLE — der minimale Fenster-Style

WS_POPUP heißt „Fenster ohne alles": keine Titelleiste, kein Rahmen, keine Systemschaltflächen. WS_VISIBLE muss dazu, weil das Fenster ja weiter sichtbar sein soll — der alte Style wird vollständig überschrieben, nicht ergänzt. Alles, was nicht in dieser Zahl steht, ist ab jetzt aus.

SWP_FRAMECHANGED — ohne das passiert nichts Sichtbares

Windows berechnet die Fensterrahmen-Geometrie zwischengespeichert. Ein geänderter Style landet zwar sofort in der internen Zahl, aber das Fenster wird erst neu vermessen, wenn man es anstößt. Genau das tut SetWindowPos mit SWP_FRAMECHANGED: „Rahmen neu berechnen." Die drei anderen Flags sagen dabei „aber Position, Größe und Fokus bitte in Ruhe lassen" — der Aufruf dient nur dem Neuberechnen.

Typisches Symptom, wenn SWP_FRAMECHANGED fehlt Die Titelleiste ist verschwunden, aber es bleibt ein Rand oder ein toter Streifen — oder der Fensterinhalt sitzt um genau die alte Titelleistenhöhe verschoben. Kein Fehler, nur falsche Geometrie: klassisches Zeichen für einen Style-Wechsel ohne Neuberechnung.

Teil 2: Nicht in der Taskleiste auftauchen

Ein Pet gehört nicht in die Taskleiste und nicht in den Alt+Tab-Wechsler. Das erledigt ein Bit im Extended Style: WS_EX_TOOLWINDOW. Der Spike setzt es zusammen mit WS_EX_LAYERED in einer einzigen Methode, die uns in Lektion 04 und 05 noch begegnet: 

private void ApplyExStyle(bool clickThrough)
{
    long ex = Win32Interop.WS_EX_LAYERED | Win32Interop.WS_EX_TOOLWINDOW;
    if (clickThrough) ex |= Win32Interop.WS_EX_TRANSPARENT;
    Win32Interop.SetWindowLongPtr(_hwnd, Win32Interop.GWL_EXSTYLE, new IntPtr(ex));
}

WS_EX_LAYERED ist die Transparenz-Voraussetzung (Lektion 01/04), WS_EX_TOOLWINDOW die Taskleisten-Frage, WS_EX_TRANSPARENT die Klick-Frage. Drei unabhängige Eigenschaften, eine Zahl.

Eine Folge, die im Spike erst im Handtest auffiel Kein Fensterrahmen + kein Taskleisten-Eintrag = keine Möglichkeit, das Programm zu beenden. Kein X, kein Rechtsklick auf ein Taskleisten-Symbol, kein Alt+F4-Ziel im Wechsler — nur noch der Task-Manager. Nachgereicht wurde deshalb ein Rechtsklick auf die Figur (Commit 7d7a829): 
private void OnMouseOver()
{
    if (Input.GetMouseButtonDown(1))
    {
        Application.Quit();
#if UNITY_EDITOR
        UnityEditor.EditorApplication.isPlaying = false;
#endif
    }
}
Merke für eigene Overlays: Ein Beenden-Weg gehört von Anfang an dazu — Rechtsklick, Tray-Icon oder Tastenkürzel. Sonst baust du eine App, die man nur abschießen kann.

Teil 3: Immer oben — und warum das nicht hält

Die Z-Reihenfolge des Desktops kennt eine Sondergruppe: Topmost-Fenster liegen über allen normalen Fenstern, egal wer den Fokus hat. Man erklärt ein Fenster dazu, indem man es bei SetWindowPos hinter das Pseudo-Handle HWND_TOPMOST (numerisch −1) einsortiert: 

public void SetTopMost(bool enabled)
{
    if (!IsActive || !enabled) return;
    Win32Interop.SetWindowPos(_hwnd, Win32Interop.HWND_TOPMOST, 0, 0, 0, 0,
        Win32Interop.SWP_NOMOVE | Win32Interop.SWP_NOSIZE | Win32Interop.SWP_NOACTIVATE);
}

Wieder das bekannte Muster: Die vier Nullen sind Attrappen, NOMOVE und NOSIZE machen sie bedeutungslos. NOACTIVATE verhindert, dass das Pet den Tastaturfokus klaut — sonst würde dir beim Tippen mitten im Satz der Cursor wegspringen.

Und jetzt der Punkt, den man ohne Praxis nicht kommen sieht: Topmost ist kein dauerhafter Zustand, auf den man sich verlassen kann. Es gibt Situationen, in denen Windows die Ordnung neu würfelt und dein Fenster nach hinten fällt:

  • Ein Spiel geht in den exklusiven Vollbildmodus (und wieder heraus).
  • Ein UAC-Prompt erscheint — der läuft auf einem eigenen, abgeschirmten Desktop.
  • Andere Programme setzen sich ihrerseits topmost und schieben dich in dieser Gruppe nach unten.
  • Bildschirmsperre, Auflösungswechsel, Monitor-Standby.

Die Lösung im Spike ist bewusst stumpf: alle 5 Sekunden nachsetzen. Der Aufruf ist billig, und dank NOACTIVATE ist er unsichtbar — er stiehlt weder Fokus noch Klicks. 

private const float TopMostReassertInterval = 5f;

// in Awake():
InvokeRepeating(nameof(ReassertTopMost), TopMostReassertInterval, TopMostReassertInterval);

/// Exklusiv-Vollbild-Spiele und UAC-Prompts stoßen jedes Fenster aus der Topmost-Ordnung.
private void ReassertTopMost()
{
    _window.SetTopMost(true);
}
Warum ein Timer und kein Event? Es gibt keine zuverlässige Benachrichtigung „du wurdest aus der Topmost-Ordnung geworfen". Man könnte Fenster-Hooks installieren oder Nachrichten abfangen — deutlich mehr Code, mehr native Fläche, mehr Bruchgefahr. Ein SetWindowPos alle 5 Sekunden kostet im Rauschen nichts. Für einen Spike ist die robuste, dumme Lösung die richtige, und sie hat im Beweis-Durchlauf (Punkt 8: Vollbild-Spiel starten und beenden → Overlay wieder oben) gehalten.

Beachte auch die Signatur: SetTopMost(bool enabled) steigt bei !enabled einfach aus. Der Spike braucht „nicht mehr topmost" nirgends — der Parameter hält die Fassade symmetrisch, ohne Code für einen Fall zu schreiben, den es nicht gibt. Willst du das später (z. B. „Pet in den Hintergrund während einer Präsentation"), ist die Erweiterung ein Dreizeiler mit HWND_NOTOPMOST (numerisch −2).

Quiz

1. Du setzt WS_POPUP, aber das Fenster sieht unverändert aus. Woran liegt es am ehesten?

Fehlendes SWP_FRAMECHANGED. Der Style ist gesetzt, aber die Rahmengeometrie ist zwischengespeichert. WS_POPUP ist korrekt ein Style (GWL_STYLE, Index −16), kein Extended Style.

2. Warum steht in SetTopMost unbedingt SWP_NOACTIVATE?

Fokus. Der Timer feuert dauerhaft im Hintergrund — ohne NOACTIVATE würde dir beim Tippen alle fünf Sekunden der Eingabefokus wegspringen. Das ist der Unterschied zwischen einem Begleiter und einem Schädling.

3. Was ist die praktische Konsequenz von WS_EX_TOOLWINDOW in Kombination mit WS_POPUP — und wie hat der Spike sie gelöst?

„Kein Schließen-Knopf und kein Taskleisten-Eintrag heißt: Es gibt keinen normalen Weg, die App zu beenden — nur den Task-Manager. Der Spike hat deshalb Rechtsklick auf die Figur als Beenden-Geste nachgerüstet (ClickFeedback.OnMouseOver + Application.Quit()). Bei jedem eigenen Overlay gehört so ein Ausgang von Anfang an in die Planung."

Was du jetzt weißt

  • Client- vs. Non-Client-Area: Der Rahmen gehört Windows — WS_POPUP | WS_VISIBLE entfernt ihn komplett.
  • SWP_FRAMECHANGED ist Pflicht nach jedem Style-Wechsel, sonst bleibt die alte Geometrie stehen.
  • WS_EX_TOOLWINDOW nimmt das Fenster aus Taskleiste und Alt+Tab — und damit jeden normalen Beenden-Weg. Ausgang selbst bauen.
  • HWND_TOPMOST ist kein stabiler Zustand: Vollbild-Spiele, UAC, Sperrbildschirm werfen dich raus → alle 5 s stumpf nachsetzen.
  • SWP_NOACTIVATE ist bei allem, was periodisch läuft, nicht optional.
