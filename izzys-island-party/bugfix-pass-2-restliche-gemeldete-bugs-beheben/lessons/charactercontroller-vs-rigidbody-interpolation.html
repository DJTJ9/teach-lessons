CharacterController vs. Rigidbody-Interpolation

Der Bowling-Ball in Izzy's Island Party zitterte beim Steuern — auch nachdem der isKinematic-Fix aus Pass 2 Batch 2 das Grundproblem (Rigidbody und CharacterController schreiben gleichzeitig auf den Transform) behoben hatte. Rest-Jitter blieb. Diese Lektion erklärt, warum.

Das Konzept: Fester Physik-Tick vs. variable Bildrate

Unity läuft zwei getrennte Taktraten gleichzeitig:

  • Rendering — läuft mit variabler Bildrate (z.B. 60, 144, 240 Hz, je nach Monitor/Last). Jeder Renderframe ruft Update() einmal auf.
  • Physik — läuft mit fester Taktrate (Time.fixedDeltaTime, Standard 0.02s = 50 Hz). Jeder Physik-Tick ruft FixedUpdate() auf.

Bei 144 Hz Rendering und 50 Hz Physik passiert FixedUpdate() nur bei manchen Renderframes. Bewegt sich ein Objekt ausschließlich in FixedUpdate(), "springt" seine Position zwischen Physik-Ticks — sie bleibt für mehrere Renderframes identisch, dann macht sie einen Sprung zum nächsten Tick.

Rigidbody löst das selbst: Mit Rigidbody.interpolation = Interpolate rendert Unity die Position zwischen zwei Physik-Ticks sanft interpoliert — der Sprung wird unsichtbar, obwohl die eigentliche Physik-Berechnung weiterhin nur 50x/Sekunde läuft.

Die Lücke: CharacterController hat das nicht

CharacterController ist kein physikgetriebenes Objekt im PhysX-Sinn. controller.Move(delta) ist ein sofortiger, kinematischer "Sweep" — Unity bewegt den Transform direkt und synchron, es gibt keinen Interpolations-Mechanismus wie bei Rigidbody.

Der Bug in PlayerControllerBowlingBattle.cs:

// VORHER — lief mit fester Physik-Taktung (50 Hz), aber ohne Interpolation
private void FixedUpdate()
{
    if (controller.enabled) Movement();   // ruft controller.Move() auf
}

Weil Move() nur 50x/Sekunde ausgeführt wurde und dabei kein Interpolationsmechanismus griff, blieb die sichtbare Ballposition zwischen den Ticks stehen und "sprang" — genau das Jitter-Muster, das beim Steuern auffiel.

Der Fix

// NACHHER — läuft mit jedem Renderframe, Time.deltaTime kompensiert die variable Bildrate
private void Update()
{
    if (controller.enabled) Movement();
}

Da StartPositionMovement() bereits move * Time.deltaTime verwendete (nicht fixedDeltaTime), war die Bewegungsberechnung selbst schon framerate-unabhängig korrekt — das einzige Problem war die Aufruf-Frequenz. Verschieben nach Update() genügte.

Merksatz: CharacterController.Move() gehört grundsätzlich in Update(), nicht in FixedUpdate() — es sei denn, die Bewegung muss exakt mit anderer Physik (Rigidbody-Kollisionen in derselben Szene) synchron sein, was bei reiner Charakter-Steuerung fast nie der Fall ist.
Quiz: Ein Rigidbody-gesteuertes Objekt (kein CharacterController) zittert leicht bei hoher Bildrate. Was ist der naheliegendste erste Check?

Quellen: Unity Manual — Rigidbody, Unity Manual — CharacterController

Zusammenfassung: Physik läuft mit fester Taktrate, Rendering mit variabler. Rigidbody kann die Lücke durch Interpolation unsichtbar machen — CharacterController kann das nicht, weil es kein PhysX-Objekt ist. Deshalb gehört CharacterController.Move() in Update(), damit es mit jedem Renderframe sauber mitläuft.
