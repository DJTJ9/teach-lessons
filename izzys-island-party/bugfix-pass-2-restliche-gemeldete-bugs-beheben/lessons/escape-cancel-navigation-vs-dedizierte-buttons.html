Escape/Cancel-Navigation vs. dedizierte Buttons

Der Controller-Select-Screen hatte einen "Zurück"-Button, der zwar funktionierte, aber schlecht aussah und andere UI überlappte. Diese Lektion ist eigentlich eine UX-Entscheidung mit einer Code-Konsequenz: wann reicht ein unsichtbares Cancel-Event, und wann braucht es einen echten Button?

Das Konzept: Zwei Wege zu "zurück"

UI Toolkit bietet für "zurück/abbrechen" zwei unabhängige Mechanismen:

  • Dedizierter Button — sichtbares Button-Element mit .clicked-Handler. Klar erreichbar per Maus, aber nimmt Platz im Layout ein und muss positioniert werden.
  • NavigationCancelEvent — ein globales, unsichtbares Event, das bei Escape (Keyboard) oder der Cancel-Taste (Gamepad, meist B/Kreis) auf dem fokussierten Element bubbelt. Braucht keinen UI-Platz.
Entscheidend: Beide Mechanismen können denselben Code-Pfad aufrufen — sie schließen sich nicht aus. Die Frage ist nicht "welcher Mechanismus", sondern "braucht dieser Screen überhaupt einen sichtbaren Button, oder reicht die unsichtbare Variante?"

Der konkrete Fall

In GameMenuEvents.cs existierte bereits vor dieser Session ein Cancel-Pfad:

root.RegisterCallback<NavigationCancelEvent>(OnControllerSelectionCancel);

private void OnControllerSelectionCancel(NavigationCancelEvent _evt)
{
    if (controllerSelectionMenu.style.display != DisplayStyle.Flex) return;
    _evt.StopPropagation();
    OnControllerSelectionBack();
}

Ein früherer Fix-Versuch hatte zusätzlich einen sichtbaren controllerSelectionBackButton eingeführt — technisch funktionsfähig, aber visuell unerwünscht (überlappte andere UI, saß mitten im Screen). Der Nutzer wollte explizit keinen Button, sondern reine Escape/Cancel-Navigation.

Der Fix war deshalb kein neuer Code, sondern Rückbau: Feld, Binding, Click-Handler und alle style.display-Toggles für den Button entfernt — der bereits vorhandene, unsichtbare Cancel-Pfad blieb unverändert der einzige Rückweg.

Merksatz: Bevor ein neuer UI-Mechanismus für "zurück" gebaut wird, prüfen, ob nicht längst ein unsichtbarer Navigation-Event-Pfad existiert, der nur falsch wahrgenommen wurde (hier: als "nicht vorhanden", weil nie mit Gamepad-Cancel getestet). Das spart nicht nur Code, sondern auch ein Layout-Problem.

Wann braucht es trotzdem einen sichtbaren Button?

Wenn der Screen auch per Maus ohne Tastatur/Gamepad bedienbar sein muss, UND kein anderes sichtbares Element "zurück" signalisiert. In diesem Fall gibt es keine Maus-Bedienung für den Controller-Select-Screen (reine Controller-/Keyboard-Interaktion vor dem eigentlichen Spielstart) — der unsichtbare Cancel-Pfad allein reicht aus.

Quiz: Ein neuer Settings-Screen soll auch mit der Maus vollständig bedienbar sein, inklusive Verlassen ohne Tastatur. Reicht NavigationCancelEvent allein?

Quelle: Unity Manual — UI Toolkit Focus & Navigation Events

Zusammenfassung: "Zurück" lässt sich per sichtbarem Button oder per unsichtbarem NavigationCancelEvent lösen — beide können denselben Code aufrufen. Die Wahl hängt davon ab, ob der Screen auch per Maus bedienbar sein muss. Vor einem neuen Rückweg-Mechanismus immer erst prüfen, ob nicht schon ein unsichtbarer Pfad existiert.
