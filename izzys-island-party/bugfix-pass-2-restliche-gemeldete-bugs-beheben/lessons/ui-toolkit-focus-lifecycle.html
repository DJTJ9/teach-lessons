UI Toolkit Fokus-Lifecycle

Zwei Bugs in dieser Session drehten sich um denselben Mechanismus: wer in UI Toolkit gerade "fokussiert" ist, und was passiert, wenn dieser Fokus verschwindet oder wechselt. Main-Menu-Enter-Doppelfeuer und der End-Screen/Pause-Menu-Konflikt sind beide Spielarten davon.

Das Konzept: Es gibt immer höchstens EIN fokussiertes Element

UI Toolkit verwaltet pro Panel einen FocusController mit genau einem focusedElement (oder null). Tastatur-Submit, Gamepad-Submit und Navigation (Pfeiltasten/Stick) wirken immer auf dieses eine Element — nicht auf "was gerade sichtbar ist".

Wichtige Events:
  • FocusInEvent / FocusOutEvent — Fokus kommt an / geht weg von einem Element
  • NavigationSubmitEvent — Submit-Taste (Enter/Gamepad-A) auf dem fokussierten Element
  • NavigationCancelEvent — Cancel-Taste (Escape/Gamepad-B), bubbled wie Submit
  • NavigationMoveEvent — Richtungsnavigation zwischen fokussierbaren Elementen

Fall 1: Main-Menu-Enter-Doppelfeuer

Ein Enter-Druck löste manchmal sofort einen Level-Load aus — nicht nur den Player-Hub öffnete. Root Cause: FocusButton() verzögerte das eigentliche .Focus() um zwei Frames per Coroutine:

private IEnumerator FocusButtonCoroutine(VisualElement _button)
{
    yield return null;
    yield return null;
    _button.Focus();   // erst hier wirklich fokussiert
}

In diesem 2-Frame-Fenster war kein Element fokussiert (oder noch das alte, bereits versteckte). Ein Navigation-Event in genau diesem Fenster konnte auf dem nächstbesten sichtbaren fokussierbaren Element landen — nicht auf dem beabsichtigten Ziel.

Der bestehende Fix (m_navigationLocked-Flag, das LoadGameScene() währenddessen blockt) hat sich in dieser Session bei Live-Tests (kurzer und langer Enter-Druck, Keyboard) bestätigt als ausreichend erwiesen.

Fall 2: End-Screen/Pause-Menu-Konflikt

Nach Spielende verlor der End-Screen manchmal den Fokus komplett (focusedElement == null) — z.B. durch einen Klick auf einen nicht-fokussierbaren Bereich (Video-Vorschau). Ohne Fokus feuert kein Submit mehr, der Continue-Button wird über Tastatur/Gamepad unerreichbar.

Die bestehende Recovery-Logik fängt das global ab:

private void OnMenuFocusOut(FocusOutEvent _evt)
{
    if (_evt.relatedTarget != null) return;       // Fokus ging zu einem ANDEREN Element — nichts tun
    if (m_lastFocusedElement == null) return;

    root.schedule.Execute(() => {
        if (root.panel.focusController.focusedElement == null)
            m_lastFocusedElement.Focus();          // nichts fokussiert? zurück zum letzten bekannten Element
    });
}

Der eigentliche neue Bug war ein anderer: ShowPauseMenu() (an die Escape-Taste gebunden) hatte keinen Guard gegen "End-Screen ist bereits offen" — Escape öffnete das Pausenmenü zusätzlich, unabhängig vom aktuellen UI-Zustand. Zwei Root-VisualElements wurden gleichzeitig sichtbar und kämpften um Darstellung.

public void ShowPauseMenu()
{
    if (resultsScreen.style.display == DisplayStyle.Flex)
    {
        FocusButton(resultScreenContinueButton);   // Fokus wiederherstellen statt Pause öffnen
        return;
    }
    if (endScreenUI.style.display == DisplayStyle.Flex)
    {
        FocusButton(endScreenRestartButton);
        return;
    }
    pauseMenu.style.display = DisplayStyle.Flex;
    FocusButton(pauseMenuResumeButton);
    FreezeTimeScale();
}
Merksatz: Jeder global gebundene Input (Escape, Pause-Button) braucht einen expliziten Check, welcher UI-Zustand gerade aktiv ist — sonst wirkt er blind "über" allem, was schon offen ist.
Quiz: Ein Button wird per style.display = DisplayStyle.None versteckt, während er fokussiert war. Was passiert mit dem Fokus?

Quelle: Unity Manual — UI Toolkit Focus

Zusammenfassung: UI Toolkit hat global genau ein fokussiertes Element. Wird es versteckt oder verschwindet der Fokus durch einen Klick ins Leere, braucht es explizite Recovery (FocusOutEvent + letztes bekanntes Element) und jeder global gebundene Input muss prüfen, welcher UI-Zustand gerade aktiv ist, bevor er einen neuen öffnet.
