PhysX Collider-Layer-Überlappung

Der Minigolf-Ball sprang gelegentlich unerklärlich in die Luft. Die Diagnose dieser Session fand eine teilweise Ursache — eine vollständige Lektion über die gefundene Mechanik, auch wenn der Bug am Ende nicht komplett gelöst wurde.

Das Konzept: Zwei Collider am selben Ort = zwei Meinungen über den Kontakt

PhysX löst pro Physik-Schritt für jedes Collider-Paar, das sich berührt oder überlappt, einen Contact mit Normale, Eindringtiefe (penetration) und Korrektur-Impuls auf. Liegen zwei unabhängige, nicht identische Collider am selben Ort, berechnet PhysX zwei getrennte Contacts — mit potenziell leicht unterschiedlicher Normale oder Eindringtiefe. Das Ergebnis: widersprüchliche Korrekturkräfte in derselben Physik-Runde.

Live-Befund in dieser Session: Jedes Track-Piece in Minigolf Mayhem hatte bereits vollständige Boden-Abdeckung über einen MeshCollider + mehrere BoxCollider-Kinder. Zusätzlich existierte ein separater "Track Surface Colliders"-Container mit eigenen flachen BoxColliders über denselben Bereichen — auf einem anderen Physics-Layer (Default statt Ground), aber die Physics-Collision-Matrix erlaubte Kollision mit beiden Layern gleichzeitig.

Wie man das findet: Collider-Overlap per Code scannen

Statt im Editor einzelne Collider manuell zu vergleichen, lässt sich das programmatisch prüfen (hier via Unity-Editor-Bridge execute_code):

var colliders = FindObjectsByType<Collider>(FindObjectsSortMode.None)
    .Where(c => !c.isTrigger && c.GetComponentInParent<Rigidbody>() == null)
    .ToArray();

for (int i = 0; i < colliders.Length; i++)
for (int j = i + 1; j < colliders.Length; j++)
{
    var a = colliders[i].bounds;
    var b = colliders[j].bounds;
    if (!a.Intersects(b)) continue;
    // echte Überlappungstiefe berechnen, nicht nur "berühren sich"
    var min = Vector3.Max(a.min, b.min);
    var max = Vector3.Min(a.max, b.max);
    if (min.x >= max.x || min.y >= max.y || min.z >= max.z) continue;
    // -> Fund: zwei Collider überlappen echt, nicht nur an der Kante
}
Fallstrick: Ein reiner Bounds.Intersects()-Check zählt auch Berührung (zwei Kacheln liegen Kante an Kante, Überlappung = 0) als Treffer. Das führte in dieser Session zu einer falschen Spur — eine "19-Meter-Naht" zwischen zwei Track-Pieces sah dramatisch aus, war bei genauer Tiefenberechnung aber nur ein normaler 0.2m-Berührungsrand. Erst die echte Schnittmenge (min < max auf allen drei Achsen) unterscheidet "berührt sich" von "überlappt wirklich".

Was half — und was nicht vollständig

Das Deaktivieren des redundanten "Track Surface Colliders"-Containers brachte spürbare Besserung, löste den Pop aber nicht vollständig. Ein Live-Capture (temporäre Debug.Log-Hooks in FixedUpdate/OnCollisionStay, nach der Diagnose wieder entfernt) zeigte: der Ball wurde bei mind. einem Vorfall auf über 14 Einheiten Höhe geschleudert — kein Jitter, ein echter, großer Impuls, korreliert mit der Shoot()-Methode. Die vollständige Ursache blieb für eine Folge-Session offen.

Merksatz: Nicht jeder "Objekt fliegt durch die Luft"-Bug ist ein Collider-Problem — manchmal ist es ein regulärer Spiel-Impuls (hier: ein Schuss-Mechanismus), der stärker oder häufiger auslöst als erwartet. Collider-Überlappung und Impuls-Mechaniken sind zwei getrennte Verdächtige, die beide geprüft werden müssen.
Quiz: Zwei Boden-Collider liegen exakt Kante an Kante (keine echte Überlappung, nur Berührung). Verursacht das typischerweise PhysX-Jitter?

Zusammenfassung: Zwei unabhängige Collider am selben Ort erzeugen zwei getrennte PhysX-Contacts, die sich widersprechen können. Collider-Überlappungen lassen sich per Code systematisch scannen — aber nur echte Interpenetration (Schnittmenge > 0 auf allen Achsen) ist verdächtig, reine Berührung ist normal. Nicht jeder "Objekt fliegt"-Bug ist ein Collider-Problem — Impuls-Mechaniken (Shoot/Move) gehören als eigener Verdächtiger auf die Liste.
